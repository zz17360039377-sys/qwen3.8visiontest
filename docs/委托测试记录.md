## 三、他的 harness 方式（如何搭建与使用）

- **服务发现**：`ss -tlnp` 探端口 + 主目录按文件名定位 `~/bigmodel/start-qwen.sh`（旁边即 gguf 与 mmproj），只运行不读源码；确认 llama-server OpenAI 兼容 API 在 `127.0.0.1:8080` 且带多模态。
- **调用**：纯标准库 `urllib.request` 手写 `/v1/chat/completions` 调用，base64 `image_url`；`temperature=0`、`enable_thinking=false`；图片长边缩 1280（小图反而放大到 256）。
- **解析**：正则抽取 + 坐标范围 clamp + 非法行剔除（自写，未用项目内任何现成代码）。
- **并发**：客户端 ThreadPoolExecutor 3 线程流水（服务端 `-np 1` 实际串行）；批量用 `nohup` 后台 + 轮询（run_all.sh 三轮，DONE.marker 标记）。
- **元数据自读**：classes.txt + 数据集 README 里正则抓 `keypoints: N`；cls 的 manifest 列序不同（`class,image`）→ 自动探测取图列。
- **自校验**：视觉链路存疑时用合成图（红底蓝圆）做 grounding 验证。
- **抽样**：manifest 按 seed=42 洗牌取前 N。

## 六、外部评测结果（tools/eval_testenv.py，独立口径）

| 数据集 | 类型 | n | 结果 |
|---|---|---|---|
| cls_armor_digit_slices | cls | 25 | 准确率 **12.0%**（3/25）——暗光小切片数字混淆严重（与此前复核结论一致） |
| cls_armor_pattern_public | cls | 25 | 准确率 **56.0%**（14/25）——清晰图案明显更好 |

| detect_rm2025_armor | detect | 30 | 类感知 P 0.9%；**类无关 P 也仅 0.9%**（IoU≥0.5 几乎无匹配）——定位本身失败，且 c0/c1/c2 占位类名使其雪上加霜（环境缺陷，见下） |
| labelme_radar_car | labelme | 12 | P 17.2% / R(已测) 28.6% / IoU 0.610 —— 密集场景（GT 每图数十框）下召回严重不足 |
| pose_droneok | pose 4kpt | 15 | **0 个有效匹配**——GT 框仅占画面 2–3%（无人机远视角），预测框高 40%，完全错位 |
| pose_okbuff2 | pose 5kpt | 15 | 匹配 10 点：MPJPE 70.7px（归一化 0.353）、PCK@0.1 = 0% —— 关键点精度不足 |

**评测期间发现并修复的评测脚本缺陷**：labelme GT 是 json 却被 YOLO 文本加载器读取（恒为空 → P 恒 0）——已接入 `load_labelme_gt`；detect 新增**类无关双口径**（P/R/IoU 不依赖类别名，应对占位类名场景）。

**结论（针对本次委托测试）**：
1. 测试代理能完全自主完成"找环境→建 harness→跑推理→自统计"全流程，遵守了沙箱与只读约束；
2. VLM 标注能力的客观结论与此前一致：清晰大目标可精准标注（luminous IoU 0.918）、暗光小切片分类差（12%）、密集场景召回不足、小目标 pose 不可用；
3. 环境侧遗留缺陷：`detect_rm2025_armor` 的占位类名（c0/c1/c2）使类感知评测无意义——需查证 RM2025-Armor-Public-Dataset 的真实类别名后回填再测；
4. 效率参考：单卡 4090 上该模型检测类 ~19–38 张/min、pose ~8–11 张/min、分类 ~170 张/min。
